# «Аким на 5 часов»: собственная multi-agent simulation без MiroFish

> Канонический дизайн после решения команды не использовать MiroFish как продукт или зависимость.  
> Первичный датасет и формула Score остаются единственным источником числовых эффектов.  
> Подробная арифметическая проверка: [аудит датасета](./track-12-dataset-audit.md).

## Решение

Использовать **подход MiroFish, но не MiroFish**: из рассчитанного городского сценария строить компактный мир заинтересованных сторон, запускать несколько агентов с разными интересами, проводить два коротких раунда реакций и собирать структурированный «Совет жителей». Команда реализует этот слой сама поверх официального детерминированного калькулятора.

```text
официальный датасет
  → валидатор пяти решений
  → детерминированный Score и audit trail
  → scenario seed только с рассчитанными фактами
  → 8–10 stakeholder agents
  → индивидуальная оценка
  → один раунд возражений
  → агрегатор конфликтов и предложения swap
  → новый Score снова считает только детерминированное ядро
```

Такой дизайн сохраняет сильные стороны MiroFish — разные персоны, взаимодействие, emergent conflicts и итоговый report — без Zep Cloud, knowledge graph, Twitter/Reddit simulation, тяжёлого развёртывания и непредсказуемого live pipeline.

## Как изменился выбор трека

После получения официального датасета трек становится **сильным финалистом**:

- формула, лаги, синергии, несовместимости и контрольные результаты уже заданы;
- весь обязательный сценарий работает локально и детерминированно;
- multi-agent слой можно показать live одним-двумя LLM-вызовами либо полностью локальным fallback;
- собственная реализация лучше демонстрирует технический вклад команды, чем запуск готового MiroFish;
- исчезают зависимости от `ZEP_API_KEY`, отдельного сервиса графа, AGPL-кода MiroFish и длительной сборки мира.

Главный оставшийся риск — не интеграция, а честность симуляции: агенты не представляют реальное общественное мнение и не должны менять официальные числа.

## Два независимых контура

### 1. City Engine — источник истины

Ядро буквально реализует выданную спецификацию:

- 5 районов и 10 показателей;
- 14 мер, стоимость, лаг и эффекты;
- ровно 5 уникальных решений;
- бюджет ≤100;
- максимум 2 меры одного направления;
- район назначения для районных мер;
- 3 синергии и 3 несовместимости;
- суммирование эффектов до единственного `clip(0,100)`;
- `D_d`, `D_avg`, `min(D_d)`, `N_crit` и официальный `Score`;
- подробный audit trail каждой дельты.

Контрольные тесты:

```text
baseline:
  D_avg = 56.8624
  min = 49.1800
  N_crit = 2
  Score = 52.55768

published example:
  D_avg = 58.0776
  min = 52.9625
  N_crit = 0
  Score = 56.54307
```

### 2. City Council — качественный AI-анализ

AI получает immutable snapshot после расчёта:

```json
{
  "scenario_hash": "sha256:...",
  "budget": {"spent": 95, "left": 5},
  "selected_measures": [],
  "district_before_after": {},
  "score_breakdown": {
    "before": 52.55768,
    "after": 56.54307,
    "d_avg": 58.0776,
    "weakest_district": "Нура",
    "n_crit": 0
  },
  "facts_agents_must_not_change": []
}
```

Агенты могут интерпретировать последствия, но не пересчитывать эффекты, не менять районы и не добавлять факты.

## Состав агентов

Для MVP достаточно 8 агентов. Тысячи агентов не добавят достоверности, но увеличат latency и стоимость.

| Агент | Главные интересы | На что реагирует |
|---|---|---|
| Житель Нуры с детьми | школы, поликлиники, транспорт | `S1`, `S2`, `T2`, районная справедливость |
| Житель Сарыарки | воздух, зелень, ЖКХ | `E1`, `E2`, `C1` |
| Житель Есиля | пробки, школы, стоимость крупных проектов | `T1`, `S1`, бюджет |
| Житель Алматы | ЖКХ, транспорт, обращения | `C1`, `T1`, `C2` |
| Житель Байконура | равномерность инвестиций | отсутствие мер и изменение `D_d` |
| Водитель | пропускная способность и безопасность дорог | `T1`, `B2`, отрицательный эффект M11 |
| Пользователь общественного транспорта | доступность и скорость ОТ | `T1`, `T2`, M1/M3 |
| Городской бюджетный аналитик | эффект на единицу стоимости, риски порогов | стоимость, вклад в Score, остаток |

Персоны — продуктовые роли, построенные из датасета. Не утверждать, что это репрезентативная выборка жителей Астаны.

## Протокол симуляции

### Раунд 1 — независимая реакция

Каждый агент возвращает строгое JSON-представление:

```json
{
  "agent_id": "nura_parent",
  "support": 0.72,
  "benefits": ["S1 вырос с 38 до 48"],
  "concerns": ["меры не улучшают T2"],
  "affected_measures": ["M7"],
  "question_to_council": "Почему транспортный дефицит остался без решения?"
}
```

`support` — не опрос и не прогноз рейтинга, а внутренняя оценка агента.

### Раунд 2 — столкновение интересов

Агенты получают только краткие результаты первого раунда. Каждый может:

- поддержать одно чужое замечание;
- возразить одному замечанию, сославшись на числовой факт;
- назвать один компромисс.

Это создаёт реальное взаимодействие, а не восемь параллельных чат-ответов.

### Агрегация

Отдельный `CouncilSynthesizer` получает структурированные ответы и возвращает:

```json
{
  "consensus": [],
  "conflicts": [],
  "underrepresented_districts": [],
  "emergent_risks": [],
  "suggested_swap": {"remove": "M10", "add": "M11", "target": "..."},
  "evidence": []
}
```

Предложенный swap не применяется автоматически. Пользователь подтверждает его, после чего City Engine валидирует набор и заново считает Score.

## Защита от галлюцинаций

1. Все числовые факты формирует City Engine.
2. Агентам передаются только поля из snapshot и закрытый список допустимых мер.
3. Ответ валидируется JSON Schema.
4. Упомянутая цифра должна совпадать с `facts_agents_must_not_change`.
5. Неизвестный район, показатель или ID меры отклоняет ответ.
6. После одной попытки repair система переходит на rule-based fallback.
7. В UI числа всегда рендерятся из engine result, никогда из текста LLM.
8. Не показывать chain-of-thought; показывать тезис и проверяемое evidence.

## Детерминированный fallback

У каждой персоны хранится utility profile:

```text
utility(agent) = Σ preference[k] × delta[agent.district,k]
               + citywide_weight × delta_city
               - ignored_need_penalty
```

Правила формируют benefits/concerns из наибольших положительных и нулевых дельт. Конфликт возникает, если два агента имеют противоположный знак utility или район не получил ни одной районной меры. Этот режим мгновенный, не требует аккаунтов и использует тот же контракт, что LLM-агенты.

В UI нужен честный badge:

- `AI council live`;
- `AI timeout → deterministic council`.

Кэшированный результат для happy path больше не обязателен.

## Игровые особенности, которые AI должен объяснять

Аудит подтвердил правильность исходных чисел, но обнаружил важные свойства формулы:

1. `N_crit` создаёт cliff: переход `39.99 → 40` примерно на балл выгоднее близкого обычного улучшения.
2. Пока Нура — минимальный район, один пункт её `D_d` влияет на Score с коэффициентом `0.7×0.16+0.3=0.412`; пункт Есиля — `0.7×0.27=0.189`.
3. Поэтому лучшие наборы концентрируют районные меры в Нуре.
4. Городские меры автоматически получают масштаб через все доли населения.
5. Открытое конечное пространство можно перебрать, поэтому «максимальный Score» сам по себе не доказывает качество управленческого решения.

Лучший найденный буквальным перебором набор:

```text
M2 город + M3 Нура + M8 Нура + M9 Нура + M14 город
стоимость = 98
Score = 57.236735
```

Именно здесь multi-agent слой полезен: он задаёт вопрос, является ли математически выгодная концентрация вложений политически и социально приемлемой для остальных районов.

## Must / Should / Cut

### Must have

- точный City Engine и validator;
- выбор ровно 5 мер и районов;
- budget guard;
- before/after по 10 показателям и 5 районам;
- breakdown четырёх компонентов Score;
- минимум 5 разных agent reactions;
- агрегированные consensus/conflicts;
- fallback без сети;
- два контрольных fixture-теста и README с одной командой запуска.

### Should have

- два раунда взаимодействия;
- suggested swap с ручным подтверждением;
- сравнение выбранного сценария с оптимальным и сбалансированным preset;
- timeline зрелости мер по кварталам;
- visual disagreement map по районам.

### Cut first

- MiroFish, Zep, Neo4j и knowledge graph;
- тысячи агентов;
- имитация Twitter/Reddit;
- настоящие GIS-слои;
- real-time городские API;
- обучение моделей;
- авторизация, multiplayer и leaderboard.

## Happy path демо — 3 минуты

1. Показать исходный город: `Score 52.55768`, Нура — слабейший район, два критических показателя.
2. Выбрать 5 мер; намеренно создать конфликт или перерасход и показать validator.
3. Запустить валидный сценарий; мгновенно получить `56.54307` и audit trail.
4. Открыть breakdown: показать, что оба показателя Нуры пересекли порог 40 и `N_crit` стал нулём.
5. Нажать `Созвать совет жителей`; показать восемь ролей, consensus и конфликт районов.
6. Принять один suggested swap; ядро повторно валидирует и считает Score.
7. Сравнить «максимум Score» и «сбалансированный сценарий».

Финальная фраза: **«Математика отвечает, что изменилось; совет агентов показывает, для кого это решение приемлемо и какой конфликт скрывает единый балл».**

## Первые 60 минут

| Время | Результат |
|---|---|
| 0–10 | Зафиксировать JSON-схемы входа, результата engine и agent response; распределить владельцев. |
| 10–25 | Реализовать pure scoring function и validator. |
| 25–35 | Добавить fixture-тесты `52.55768`, `56.54307`, порядок мер и `clip`. |
| 10–35 параллельно | Собрать один UI-экран на mock result. |
| 35–45 | Соединить UI и engine; показать breakdown Score. |
| 35–50 параллельно | Реализовать 8 persona configs и rule-based fallback. |
| 50–60 | Первый end-to-end проход и запись экрана; только после него подключать LLM. |

## Оценка по таблице жюри

Это не гарантированный прогноз, а реалистичный диапазон при доказательном демо.

| Критерий | Вес | Цель | Evidence |
|---|---:|---:|---|
| Соответствие и работоспособность | 25 | 23–25 | официальный score, validator, 5 решений, два сценария, fallback |
| Техническая реализация | 25 | 21–25 | чистый engine, schema-validated agents, два раунда, timeout, тесты |
| README и воспроизводимость | 25 | 21–25 | одна команда запуска, режим без ключа, формула, fixtures, архитектура |
| Ценность и применимость | 15 | 12–14 | сравнение эффективности и справедливости, понятный управленческий выбор |
| Оригинальность | 10 | 8–10 | собственный multi-agent council, взаимодействие, swap с пересчётом |
| **Ориентир** | **100** | **85–99** | диапазон зависит от качества реализации и защиты |

Причины крупных потерь: LLM считает числа; базовый сценарий требует аккаунт; агенты не взаимодействуют; отсутствует fallback; формула не воспроизводит fixtures; MiroFish-подобная риторика выдаётся за реальный прогноз общественного мнения.

## Итоговая формулировка продукта

**«Аким на 5 часов» — проверяемая бюджетная песочница с собственным AI-советом жителей: детерминированный движок считает последствия пяти решений, а взаимодействующие агенты выявляют конфликт интересов районов и предлагают человеку один проверяемый вариант перераспределения.**

Это сильнее исходной интеграции MiroFish для пятичасового формата: меньше риск, яснее вклад команды, быстрее live demo и выше воспроизводимость — при сохранении самой полезной идеи multi-agent simulation.

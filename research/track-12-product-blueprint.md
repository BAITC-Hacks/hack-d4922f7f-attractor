# «Аким города»: продуктовый и технический blueprint

Дата: 23 сентября 2026 года  
Статус: рабочий план на основе выданного датасета и его арифметического аудита  
Связанные материалы: [аудит датасета](./track-12-dataset-audit.md), [дизайн агентной симуляции](./track-12-akim-agent-simulation.md)

## Решение в одном абзаце

Строить не чат-бота и не «цифровой двойник Астаны», а **интерактивный штаб городских решений по принципу MiroFish**. Пользователь выбирает ровно пять мер в пределах бюджета, детерминированный City Engine буквально воспроизводит официальную формулу и возвращает проверяемый Score. Затем система превращает результат в `reality seed`, создаёт разных городских стейкхолдеров, проводит два раунда их взаимодействия и формирует отчёт о коалициях, конфликтах и компромиссах. Это лучший баланс для хакатона: числовое ядро можно автоматически проверить, а multi-agent слой даёт сильный и содержательный AI-сценарий.

### Что означает «по принципу MiroFish» в этом продукте

Официальный MiroFish строит граф сущностей из seed-материалов, генерирует персоны, запускает их взаимодействие в социальной среде и затем собирает prediction report. Мы сохраняем эту причинную цепочку, но уменьшаем её до масштаба задания:

```text
официальный датасет + выбранные меры
  → точный City Engine result
  → reality seed с районами, мерами, эффектами и интересами
  → stakeholder graph: кто затронут и чьи интересы пересекаются
  → 8–12 агентов с разными районами, целями и influence weight
  → раунд 1: независимая реакция
  → раунд 2: ответы, поддержка, возражения и формирование коалиций
  → Report Agent: consensus, conflicts, blind spots, suggested swap
  → повторный расчёт swap только через City Engine
```

MVP не имитирует Twitter/Reddit и не претендует на прогноз реального общественного мнения. Это decision rehearsal: способ найти реакции и вопросы, которые затем нужно проверять реальными данными. Такой предел соответствует и публичному описанию MiroFish, где prediction report не называется гарантированным прогнозом.

## 1. Что именно, вероятно, будет оценивать проверяющий агент

Это вывод из структуры задания и контрольных примеров, а не подтверждённая схема скрытого evaluator.

### Почти наверняка проверяемое ядро

- входной датасет читается без ручной подготовки;
- выбираются ровно пять уникальных мер;
- бюджет не превышает 100;
- соблюдается максимум двух мер одного направления;
- для районных мер указан допустимый район;
- несовместимые пары отклоняются;
- эффекты лага, синергии и отрицательные дельты применяются в правильном порядке;
- `clip(0, 100)` выполняется после суммирования эффектов;
- рассчитываются `D_d`, `D_avg`, `min(D_d)`, `N_crit` и итоговый `Score`;
- базовый fixture даёт `52.55768`, опубликованный пример — `56.54307`;
- одинаковый вход всегда даёт одинаковый JSON-результат.

### Поэтому интерфейс и AI не должны быть источником истины

Официальный расчёт нужно оформить как чистую функцию:

```text
evaluate(dataset, selection) -> EvaluationResult
```

Вход и выход сериализуемы в JSON. UI, оптимизатор и AI Council являются клиентами одной функции. LLM нельзя давать право менять цифры, выбирать формулу или исправлять невалидный набор.

### Минимальный CLI-контракт

```bash
python -m city_engine evaluate \
  --dataset data/city.json \
  --selection fixtures/published-example.json \
  --output result.json
```

Коды завершения:

- `0` — результат рассчитан;
- `2` — вход не прошёл schema validation;
- `3` — набор решений нарушает игровые правила;
- `4` — внутренняя ошибка расчёта.

Это позволяет пережить сценарий, в котором жюри запускает собственный датасет без UI.

## 2. Рынок: решения есть, но они закрывают разные половины задачи

### Основные классы аналогов

| Класс | Что уже существует | Что можно взять как паттерн | Почему это не прямой заменитель |
|---|---|---|---|
| Participatory AI | UrbanistAI объединяет генеративный AI, совместное проектирование, оценку идей и голосование | понятное вовлечение стейкхолдеров, визуализация вариантов, режим обсуждения | продукт сфокусирован на participatory planning и визуальном co-design, а не на точном воспроизведении закрытой формулы бюджетного сценария |
| Городской мониторинг | UN-Habitat Global Urban Monitoring Framework объединяет городские показатели, требует дезагрегации и внимания к исключённым группам | разрез по районам, прозрачные показатели, акцент на неравенстве | это рамка мониторинга, а не готовый игровой decision engine |
| Композитные индексы | OECD/JRC даёт методологию построения, нормализации, взвешивания и проверки composite indicators | открытая формула, sensitivity и честная трактовка весов | методология не содержит конкретной модели мер и бюджета из задания |
| Participatory digital twins | EU Local Digital Twin Participate связывает городские сценарии с вовлечением жителей и приоритизацией инициатив | сценарии + обратная связь + подтверждённый общественный мандат | требует более широкого городского контура и реальных процессов участия |
| Локальные smart-city системы | Smart City Астаны и iKOMEK показывают наличие городских данных и операционного управления | локальный язык, реальные домены, знакомый контекст обращений и сервисов | открытые материалы не дают готовой причинной модели «мера → изменение всех показателей» |

### Рыночная ниша для демо

**Не:** «AI управляет городом» или «мы построили цифровой двойник».  
**Да:** «Decision rehearsal cockpit: проверяет бюджетный сценарий, объясняет его числовой эффект и вскрывает конфликт интересов до принятия решения».

Защищаемое отличие — соединение трёх слоёв в одном коротком потоке:

1. точный и воспроизводимый расчёт официального Score;
2. визуальное объяснение изменений по районам и показателям;
3. структурированный AI-анализ стейкхолдеров с цитируемыми фактами из расчёта.

## 3. Что брать готовым, а что написать самим

### Брать готовым

- `Pydantic` или JSON Schema для входных/выходных контрактов;
- `FastAPI` для тонкого API вокруг чистого движка;
- `React + TypeScript + Vite` для одного быстрого интерфейса;
- `Recharts` или `ECharts` для dumbbell/bar charts и breakdown;
- любой OpenAI-совместимый API только за серверным adapter;
- Docker Compose для воспроизводимого запуска.

### Писать самим

- чистый City Engine и валидатор правил;
- exhaustive optimizer по небольшому пространству решений;
- audit trail до каждой дельты;
- utility profiles восьми персон и детерминированный fallback;
- агрегатор конфликтов и suggested swap;
- предметный UI «штаб решений».

### Не брать в MVP

- MiroFish, Zep, Neo4j и другой graph stack;
- обучение модели или fine-tuning;
- реальные GIS-слои;
- полный OASIS social-media runtime;
- авторизацию, роли, историю пользователей;
- реальные городские API, если они не входят в evaluator.

Полный стек MiroFish увеличивает поверхность отказа: оригинальный pipeline включает knowledge graph/memory, генерацию профилей, OASIS simulation и отдельный ReportAgent. Для хакатона восемь–двенадцать персон, два раунда и один Report Agent проще выразить несколькими параллельными structured-output вызовами и единым fallback-контрактом. При этом продукт сохраняет основную механику MiroFish: seed → world → autonomous reactions → social influence → report.

## 4. Архитектура

```text
                    ┌─────────────────────┐
                    │ React decision desk │
                    └──────────┬──────────┘
                               │ REST/JSON
                    ┌──────────▼──────────┐
                    │ FastAPI application │
                    └──────┬────────┬─────┘
                           │        │
             ┌─────────────▼─┐   ┌──▼────────────────┐
             │  City Engine  │   │ MiroFish-like Lab │
             │ pure function │   │ agents / fallback │
             └──────┬────────┘   └──┬────────────────┘
                    │               │ read-only snapshot
        ┌───────────▼──────────┐    │
        │ dataset + rule schema│◄───┘
        └──────────────────────┘
```

### Главные контракты

`Selection`:

```json
{
  "dataset_version": "official-v1",
  "items": [
    {"measure_id": "M7", "district_id": "nura"},
    {"measure_id": "M12", "district_id": null}
  ]
}
```

`EvaluationResult`:

```json
{
  "input_hash": "sha256:...",
  "engine_version": "1.0.0",
  "valid": true,
  "budget": {"spent": 95, "limit": 100},
  "score": {"before": 52.55768, "after": 56.54307, "delta": 3.98539},
  "districts": {},
  "indicators": {},
  "score_breakdown": {},
  "audit": []
}
```

`CouncilResult` всегда содержит `source: live-ai | deterministic-fallback`, `scenario_hash`, ссылки на IDs районов/мер и только факты, присутствующие в `EvaluationResult`.

Каждый агент хранит не длинную биографию, а компактное проверяемое состояние:

```json
{
  "id": "nura_parent",
  "district": "nura",
  "priorities": {"S1": 1.0, "S2": 0.8, "T2": 0.6},
  "trust": {"akimat": 0.55, "budget_analyst": 0.7},
  "influence": 0.65,
  "stance": 0.0,
  "memory": []
}
```

Раунд 1 обновляет `stance` только на основе рассчитанных эффектов. В раунде 2 агент видит короткие тезисы соседей по stakeholder graph, может поддержать или оспорить один тезис и обновляет stance в ограниченном диапазоне. Все сообщения сохраняются как события; Report Agent агрегирует их, но не переписывает историю.

## 5. UI-концепция: «Стол акима»

### Основной экран

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ Астана / горизонт 8 кварталов     Бюджет 74 / 100      4 из 5 решений       │
├───────────────────┬───────────────────────────────────┬──────────────────────┤
│ Портфель мер      │ Карта пяти районов               │ Решение              │
│                   │                                   │                      │
│ Транспорт      2  │      [Есиль 63.0]                │ Score                │
│ Экология       0  │ [Сарыарка] [Нура 49.2 → 53.0]    │ 52.56 → 56.54       │
│ Соц. сфера     1  │      [Алматы] [Байконур]         │ +3.99                │
│ Безопасность   0  │                                   │                      │
│ Сервис         1  │ выбранная мера рисует связи       │ Среднее / минимум / │
│                   │ с затронутыми показателями        │ критические точки   │
├───────────────────┴───────────────────────────────────┴──────────────────────┤
│ Временная шкала: сейчас ─ Q1 ─ Q2 ─ Q3 ─ Q4 ─ Q5 ─ Q6 ─ Q7 ─ Q8           │
├──────────────────────────────────────────────────────────────────────────────┤
│ [Проверить сценарий]  [Созвать совет жителей]       Ошибки/синергии/конфликты│
└──────────────────────────────────────────────────────────────────────────────┘
```

После расчёта правая панель раскрывается в три вкладки:

- **Результат** — before/after и вклад компонентов Score;
- **Почему** — audit trail по мерам, лагам, синергиям и threshold effects;
- **Совет жителей** — consensus, конфликт районов, слабопредставленные интересы и один proposed swap.

### Визуальное направление

- Палитра: `Government ink #172033`, `Paper #F4F5F2`, `Civic blue #2D5BFF`, `Budget amber #D98B19`, `Critical red #C43D3D`, `Positive green #16836B`.
- Типографика: `Manrope` для интерфейса и крупных чисел; системный fallback без блокировки загрузки. Цифры — tabular.
- Главный визуальный объект — схематичная карта пяти районов, а не hero-gradient и не сетка одинаковых карточек.
- Формы строгие: радиус 6–8 px только у интерактивных элементов; секции разделяются геометрией и линиями.
- Единственная заметная анимация — переход карты и Score из before в after после расчёта; `prefers-reduced-motion` отключает её.

### Состояния, которые обязаны выглядеть хорошо

1. пустой набор — объясняет правило пяти решений;
2. частичный набор — показывает остаток бюджета и незакрытые ограничения;
3. невалидный — блокирует расчёт и указывает конкретную конфликтующую пару;
4. рассчитанный — фиксирует hash/version и показывает before/after;
5. AI загружается — Score уже доступен, совет не блокирует UI;
6. AI недоступен — тот же интерфейс показывает deterministic council с честным badge.

### Что даст «вау» без технического риска

- наведение на изменение Score подсвечивает район и показатели, которые дали вклад;
- переключатель `Оптимум / Сбалансированный / Мой сценарий` мгновенно меняет карту;
- «рентген формулы» показывает, что устранение `N_crit` дало дискретный выигрыш;
- suggested swap можно применить в черновик, но только City Engine подтверждает новый результат.

## 6. Разделение работы на трёх человек

Работа делится по стабильным интерфейсам, а не по слоям «frontend/backend/AI», которые сходятся слишком поздно.

### Участник A — числовое ядро и evaluator compatibility

Владеет:

- схемой официального датасета;
- `evaluate()` и validator;
- audit trail и exhaustive optimizer;
- fixtures `52.55768` и `56.54307`;
- CLI и unit tests.

Первый контракт через 30 минут: `EvaluationResult` для двух fixtures. До этого момента не занимается API, Docker или UI.

### Участник B — продуктовый UI и визуализация

Владеет:

- single-screen decision desk на mock `EvaluationResult`;
- выбором пяти мер, budget meter и состояниями ошибок;
- схемой районов, before/after, breakdown и timeline;
- адаптивностью, focus states и demo polish.

Первый контракт через 30 минут: кликабельный экран с mock JSON, включая invalid и calculated states.

### Участник C — интеграция, AI Council и воспроизводимый запуск

Владеет:

- FastAPI endpoints и OpenAPI;
- persona configs, structured-output prompt, validation и fallback;
- соединение UI ↔ engine;
- Dockerfiles, Compose, `.env.example`, healthchecks;
- README, demo fixtures и резервная запись.

Первый контракт через 30 минут: `/health`, `/evaluate` на stub и `CouncilResult` fallback. AI подключается только после end-to-end пути.

### Общие точки синхронизации

| Время | Обязательный результат | Кто блокирует переход |
|---|---|---|
| 00:15 | заморожены три JSON-контракта | все трое |
| 00:30 | fixture engine, UI на mock, API stub | каждый владелец |
| 01:00 | первый end-to-end сценарий без AI | C |
| 02:00 | все validation states и audit trail | A + B |
| 03:00 | Council live либо fallback за тем же контрактом | C |
| 04:00 | чистый Docker Compose запуск | C, проверяют A + B |
| 04:30 | два полных прогона демо; feature freeze | все трое |

Правило интеграции: A и B не ждут друг друга — они работают через заранее сохранённый `fixtures/published-result.json`. C меняет stub на реальную функцию, не меняя контракт.

## 7. План полного MVP за 3–4 часа на троих

Цель — рабочий, демонстрируемый MVP через **3 часа 30 минут**. Четвёртый час является резервом на чистый запуск, блокеры и репетицию, а не временем для новых функций.

| Время | Разработчик A — Engine | Разработчик B — UI | Разработчик C — Agents + integration | Общий gate |
|---|---|---|---|---|
| 00:00–00:15 | утверждает domain schema и формулу | утверждает экран и UI states | утверждает agent/council schema | контракты заморожены |
| 00:15–00:45 | baseline + published fixture | shell экрана, выбор мер, budget bar на mock | API stub, 6–8 persona configs, fallback skeleton | у всех есть локально проверяемый результат |
| 00:45–01:15 | validator, conflicts, lag/synergy/clip | invalid/partial/calculated states | соединяет UI с engine, `/health`, `/evaluate` | первый end-to-end без AI |
| 01:15–02:00 | audit trail + critical tests | before/after районов + Score breakdown | раунд 1, раунд 2, Report Agent по общей JSON Schema | основной продуктовый сценарий работает |
| 02:00–02:30 | CLI evaluator entrypoint | Council panel + swap preview | live structured output, timeout и fallback | MiroFish-like flow работает либо честно падает в fallback |
| 02:30–03:00 | smoke/regression tests | responsive polish и ошибки | Compose, `.env.example`, README | чистый запуск одной командой |
| 03:00–03:30 | чинит только P0/P1 | чинит только P0/P1 | два демо-прогона, backup fixtures | feature freeze и полный MVP |
| 03:30–04:00 | резерв | резерв | резерв | только блокеры и запись демо |

### Scope, который помещается в 3–4 часа

Обязательно:

- pure City Engine с двумя точными fixtures;
- выбор пяти мер, budget/conflict guard;
- один основной экран с before/after и Score breakdown;
- 6–8 фиксированных stakeholder agents;
- два раунда: независимая реакция и одно взаимодействие;
- один Report Agent: consensus, conflict, blind spot, suggested swap;
- rule-based fallback по тому же контракту;
- CLI или API для evaluator;
- Docker Compose и короткий README.

Только если к 2:30 всё зелёное:

- exhaustive optimum preset;
- hover-подсветка вклада факторов;
- плавная анимация карты;
- второй вариант визуализации или дополнительные персоны.

Запрещено начинать в этом окне:

- Neo4j/Zep/OASIS, настоящий social feed и long-term memory;
- GIS-карта, авторизация, база данных;
- загрузка произвольных PDF и RAG;
- больше двух agent rounds;
- мобильная версия сверх базовой адаптивности.

### Stop rules

- Если к `01:15` нет пути `выбор → result.json → UI`, вся команда чинит интеграцию; AI-подключение откладывается.
- Если live AI не даёт schema-valid ответ за 20 минут, включается deterministic fallback; контракт не меняется.
- Если Compose не запускается к `03:00`, UI и API упрощаются до одного процесса; новые функции запрещены.
- После `03:15` разрешены только блокеры, текст демо и резервные fixtures.

## 8. Порядок приоритетов при нехватке времени

1. правильный City Engine;
2. один цельный UI flow;
3. audit trail;
4. deterministic Council;
5. live LLM;
6. анимации и дополнительные режимы.

Если убрать live LLM, продукт остаётся полноценным. Если убрать точный расчёт или ясный UI, он перестаёт отвечать заданию.

## 9. Definition of Done

- два контрольных результата совпадают до заданной точности;
- десять ключевых правил имеют unit tests;
- evaluator работает из CLI без браузера и сети;
- UI не может отправить заведомо невалидный сценарий;
- Score и все числа в UI приходят только из City Engine;
- AI-ответ проходит schema/fact validation или заменяется fallback;
- `docker compose up --build` поднимает систему с нуля;
- полный demo path занимает не больше трёх минут;
- интерфейс явно говорит, что персоны — сценарная модель, а не репрезентативный опрос жителей.

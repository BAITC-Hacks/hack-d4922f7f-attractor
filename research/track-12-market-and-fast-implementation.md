# Трек «Аким города»: рынок, готовые компоненты и быстрый план реализации

> Дата проверки: 23 сентября 2026 года  
> Метод: локальная спецификация и аудит датасета + первичные источники владельцев продуктов и официальная документация.  
> Статус: исследование для хакатонного MVP, не модель реального городского управления.

## Короткий вывод

Рынок подтверждает сам класс продукта, но не даёт готового решения, которое буквально закрывает условия трека. ArcGIS Urban, UrbanFootprint и MIT CityScope уже умеют сравнивать городские сценарии и показатели; Decidim закрывает участие жителей и бюджетный выбор; существующий Astana Smart City и цифровой двойник подтверждают локальный спрос на data-driven управление. Однако их публичная документация не описывает комбинацию из пяти решений, жёсткого бюджета, официальной формулы Quality of Life Score и объясняющего multi-agent «совета жителей».

Для хакатона **не нужно интегрировать тяжёлую городскую платформу**. Самый быстрый и надёжный путь — собственное детерминированное ядро поверх выданного датасета, один качественный dashboard и один опциональный LLM-вызов со Structured Outputs. Готовые продукты полезны как доказательство рынка и источник UX-паттернов, а не как runtime-зависимости.

## 1. Что именно должен проверить evaluator

### Факты из локальных первичных материалов

Выданный датасет уже содержит полный вычислительный контракт:

- 5 районов, 10 показателей и доли населения;
- 14 мер со стоимостью, направлением, лагом и эффектами;
- ровно 5 уникальных решений, бюджет не более 100 и максимум 2 меры одного направления;
- район назначения для районных мер;
- 3 синергии и 3 несовместимости;
- формулы `D_d`, `D_avg`, `min(D_d)`, `N_crit` и итогового `Score`;
- контрольные результаты `52.55768` для baseline и `56.54307` для опубликованного сценария.

Источник: [локальный аудит датасета](./track-12-dataset-audit.md) и [канонический дизайн решения](./track-12-akim-agent-simulation.md).

### Вывод для реализации

Наиболее вероятный автоматический evaluator будет подавать подготовленный набор данных/сценарий и сравнивать валидность и числовой результат. Поэтому контракт должен быть отделён от UI и LLM:

```text
dataset.json + scenario.json
  -> validateScenario()
  -> calculateScenario()
  -> result.json
```

Минимальный `result.json`:

```json
{
  "valid": true,
  "errors": [],
  "scenario_hash": "sha256:...",
  "budget": {"spent": 95, "left": 5},
  "district_scores": {},
  "d_avg": 58.0776,
  "min_district": {"id": "nura", "score": 52.9625},
  "n_crit": 0,
  "score": 56.54307,
  "audit": []
}
```

Обязательные свойства: один и тот же вход даёт один и тот же результат; порядок выбранных мер не влияет на ответ; эффекты сначала суммируются, `clip(0,100)` применяется один раз; округляется только отображение; LLM никогда не участвует в расчёте.

## 2. Решения на рынке

| Решение | Подтверждённая функция | Что можно позаимствовать | Почему не заменяет наш MVP |
|---|---|---|---|
| **ArcGIS Urban** | Создание и сравнение land-use/zoning сценариев, расчёт метрик, dashboards и 3D-визуализация. [Документация сценариев](https://doc.esri.com/en/arcgis-urban/latest/help/help-scenarios.html), [официальный обзор](https://www.esri.com/en-us/arcgis/products/arcgis-urban/features/3d-scenario-modeling) | Переключатель baseline/scenario, мгновенные метрики, карта как контекст | Требует лицензии; предметная модель — земля, зонирование и застройка, а не пять мер из датасета трека |
| **UrbanFootprint** | Сценарии развития и оценка воздействия на emissions, accessibility, mobility, risk/resilience, water и energy. [Официальное руководство](https://urbanfootprint.com/wp-content/uploads/2020/02/Getting-Started-with-UrbanFootprint.pdf) | Сравнение сценариев по нескольким эффектам и прозрачные KPI | Готовая коммерческая аналитическая платформа, не evaluator-compatible движок нашего кейса |
| **MIT CityScope / CityScopeJS** | Open-source семейство инструментов для urban simulation и community engagement; web-интерфейс сравнивает варианты по KPI и подключает traffic, ABM, noise, storm-water и access. [Обзор](https://cityscope.media.mit.edu/), [CityScopeJS](https://cityscope.media.mit.edu/cityscopejs/Introduction/) | Модульная схема «input -> analytics modules -> KPI», сценарное взаимодействие | Слишком широкий research framework; интеграция модулей не нужна для фиксированного маленького датасета |
| **Decidim** | Open-source платформа муниципального участия; поддерживает strategic planning и participatory budgeting, включая выбор проектов в пределах бюджета. [Документация](https://docs.decidim.org/), [Budgets](https://docs.decidim.org/en/develop/admin/components/budgets.html) | UX бюджетной корзины, районные предложения, accountability | Это платформа реального участия граждан, а не симулятор эффектов и не AI-совет |
| **Mesa** | Apache-2.0 Python framework для agent-based modeling с агентами, scheduler/grid, сбором данных и browser visualization. [Официальная документация](https://mesa.readthedocs.io/stable/) | Если понадобится настоящая пошаговая ABM после хакатона | Для 8 фиксированных персон и двух раундов добавляет лишний framework и второй UI-стек |
| **Astana Smart City / цифровой двойник** | Акимат определяет Smart City как повышение эффективности ресурсов и услуг; приоритеты включают безопасность, транспорт, ЖКХ, образование, здравоохранение и управление. Отдельный проект цифрового двойника связан прежде всего с видеонаблюдением и AI-видеоаналитикой. [Smart City](https://www.gov.kz/memleket/entities/astana/activities/14795?lang=ru), [цифровой двойник](https://www.gov.kz/memleket/entities/astana/press/news/details/938778?lang=ru) | Сильный локальный контекст и правильные домены продукта | Публичные материалы не показывают управленческую бюджетную песочницу с общей QoL-формулой и симуляцией конфликта интересов |

### Рыночная ниша — вывод, а не подтверждённый факт

По проверенным публичным источникам ниша выглядит так: **explainable city-policy sandbox**, где руководитель сравнивает ограниченные бюджетом решения, видит точный вклад каждой меры в единый score и отдельно оценивает конфликт эффективности и районной справедливости. Утверждать, что прямого аналога вообще не существует, нельзя; корректная формулировка — «прямой аналог не найден в проверенных официальных материалах».

## 3. Какие готовые компоненты реально ускорят MVP

### Рекомендуемый стек

1. **Детерминированное ядро на TypeScript или Python без framework.** Формула мала; чистая функция будет проще, быстрее и безопаснее для evaluator, чем Mesa, LangGraph или полноценный digital twin.
2. **React/Next.js + существующая component library проекта.** Один экран, локальное состояние, без БД и авторизации.
3. **Recharts/ECharts для before/after.** Нужны bar/radar и waterfall, а не сложная GIS-аналитика.
4. **MapLibre GL JS — только если в датасете есть/будет геометрия районов.** MapLibre — WebGL TypeScript-библиотека для интерактивных карт и vector tiles; quickstart не требует собственного GIS-backend. [Официальная документация](https://maplibre.org/maplibre-gl-js/docs/). Если геометрии нет, стилизованные карточки районов честнее и быстрее псевдокарты.
5. **OpenAI Responses API + Structured Outputs — опционально.** Официальная документация подтверждает соответствие ответа заданной JSON Schema и рекомендует Structured Outputs вместо обычного JSON mode. [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Для этого кейса достаточно одного параллельного запроса на 5–8 персон и одного агрегированного JSON, а не тяжёлой multi-agent orchestration.
6. **Rule-based fallback обязателен.** По таймауту или без ключа UI получает тот же schema-valid результат из локальных utility-профилей.

### Что не брать в runtime

- ArcGIS Urban/UrbanFootprint: лицензирование, внешняя модель данных и лишняя интеграция.
- MIT CityScope/Mesa: полезны как reference, но не сокращают реализацию фиксированной формулы.
- Decidim: слишком тяжёлый Rails-контур для одного демо.
- полноценный Agents SDK: официально он поддерживает tools, orchestration и state ([документация](https://developers.openai.com/api/docs/guides/agents/sdk)), но в этом MVP один структурированный вызов проще и надёжнее.
- настоящие GIS, traffic simulation, knowledge graph, RAG и vector database: их нет в критерии результата.

## 4. UI, который выглядит как продукт, а не форма с графиками

### Один основной экран

```text
┌─────────────── header: Scenario / Score / budget / Run ───────────────┐
│ Левая колонка             │ Центр                    │ Правая колонка │
│ 14 мер по 5 доменам       │ 5 районов: before/after │ Score breakdown│
│ фильтр + стоимость + лаг  │ weakest/critical badges │ audit trail    │
│ выбранные 5 и conflicts   │ domain heatmap          │ AI Council     │
└───────────────────────────────────────────────────────────────────────┘
```

Ключевые состояния:

- sticky budget bar `95 / 100` и счётчик `5 / 5`;
- невалидная мера блокируется до запуска и объясняет конкретное правило;
- после расчёта числа анимируются один раз, но остаются сравнимыми (`до` всегда рядом с `после`);
- score раскрывается на `0.7 × D_avg`, `0.3 × min(D_d)` и `−1 × N_crit`;
- audit trail отвечает «какая мера, какой показатель, лаг, синергия, итоговая дельта»;
- AI Council показывает не чат, а три секции: `консенсус`, `конфликты`, `предлагаемый swap`; swap сначала preview, затем ручное подтверждение и новый точный расчёт;
- badge явно различает `AI live` и `deterministic fallback`.

### Главный demo-story

Не продавать «ИИ предсказывает жителей». Продавать контраст:

1. математический оптимум концентрирует районные меры в Нуре;
2. score растёт и критические показатели исчезают;
3. совет показывает, какие районы не получили прямой инвестиции;
4. пользователь сравнивает максимум score со сбалансированным сценарием.

Это сильнее декоративной 3D-карты: UI делает видимой механику датасета и показывает управленческий компромисс.

## 5. Разделение работы на трёх человек

| Владелец | Зона ответственности | Контракт на стыке | Готово, когда |
|---|---|---|---|
| **1. Engine / evaluator** | Парсер датасета, validator, pure scoring function, audit trail, fixtures, CLI/API | `scenario.json -> result.json` | Тесты точно дают `52.55768` и `56.54307`; порядок мер не влияет; все invalid cases покрыты |
| **2. Product UI** | Design tokens, выбор мер, budget/conflict UX, районный before/after, score breakdown, comparison view | Работает сначала на замороженном `result.fixture.json`, затем на engine | Весь happy path проходит без LLM; desktop 1440 и laptop 1280 читаемы; loading/error/fallback состояния готовы |
| **3. AI council + integration/demo** | Persona configs, structured output schema, один live вызов, deterministic fallback, timeout/cache, Docker/README и demo fixtures | Получает только immutable `result.json`, возвращает `council.json`; никогда не меняет score | Без ключа выдаёт fallback; с ключом schema-valid ответ; timeout не ломает UI; одна команда запуска |

Правило параллельной работы: в первые 15 минут владельцы фиксируют две JSON Schema (`result` и `council`) и больше не меняют их без общего согласования. UI не ждёт backend, AI не читает сырой датасет, engine не знает о React или LLM.

## 6. Реализация за 3–4 часа

| Время | Engine | UI | AI / integration |
|---|---|---|---|
| 0:00–0:15 | Заморозить result schema | Заморозить layout/states | Заморозить council schema |
| 0:15–0:45 | Baseline + published fixture | Shell + selection/budget на mock | API stub + 6–8 personas + fallback |
| 0:45–1:15 | Validator + formula | Invalid/calculated states | Первый end-to-end без AI |
| 1:15–2:00 | Audit trail + critical tests | District comparison + breakdown | Два agent rounds + Report Agent |
| 2:00–2:30 | CLI evaluator entrypoint | Council + swap preview | Structured Output + timeout/fallback |
| 2:30–3:00 | Smoke tests | Responsive/error polish | Docker + README + clean run |
| 3:00–3:30 | Только P0/P1 | Только P0/P1 | Два demo rehearsal + backup fixtures |
| 3:30–4:00 | Резерв | Резерв | Резерв; никаких новых функций |

Критический stop rule: если к 1:15 не работает `selection -> result.json -> UI`, live AI откладывается до восстановления вертикального сценария. Если structured output не стабилен за 20 минут, demo использует deterministic council по тому же контракту.

## 7. Критические риски и решения

| Риск | Решение |
|---|---|
| Evaluator вызывает код не через UI | Отдельный CLI/API entrypoint с документированным JSON-контрактом |
| Неизвестна точная схема входного файла | Сделать тонкий adapter; нормализованная domain schema не зависит от формата файла |
| LLM завис или вернул отказ | Таймаут 5–8 секунд, Structured Outputs, затем локальный fallback |
| Жюри считает AI-реакции выдуманным соцопросом | Label «сценарные персоны, не репрезентативный прогноз»; все числа только из engine |
| UI прячет механику score | Breakdown и audit trail всегда доступны рядом с итоговым числом |
| Команда тратит время на карту | Карта только при готовом GeoJSON; иначе district cards/heatmap |
| Оптимум находится перебором и убивает игровую глубину | Показывать одновременно эффективность, слабейший район, критические пороги и распределение прямых инвестиций |

## Итоговая рекомендация

Позиционировать продукт как **«цифровой штаб акима: проверяемая бюджетная песочница + AI-совет районов»**. Доказательная часть — точный engine и audit trail; визуальная часть — сравнение сценариев и конфликт эффективности/справедливости; AI — ограниченный качественный слой с фиксированной схемой и fallback. Это использует сильнейшую часть готового датасета, соответствует вероятному evaluator и остаётся реализуемым тремя людьми за один хакатонный спринт.

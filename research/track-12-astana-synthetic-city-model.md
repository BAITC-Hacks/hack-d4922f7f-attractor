# Синтетическая Астана: модель города и UI

Дата: 23 сентября 2026 года  
Статус: продуктовая концепция MVP для трека «Аким города»

## Короткое решение

Астану следует представить не как детальную 3D-копию, а как **синтетический управленческий двойник**: пять районов, десять показателей качества жизни, инфраструктурные объекты, бюджетные меры и население с разными интересами.

Числовое ядро работает по официальному датасету и детерминированной формуле. Multi-agent слой по принципу MiroFish не меняет числа, а моделирует реакции, конфликты и образование коалиций. UI использует подход CoSI: карта является главным рабочим объектом, а все показатели и сценарии привязаны к территории.

## 1. Модель города

```text
Астана
├── 5 районов
│   ├── население и его доля
│   ├── 10 показателей качества жизни
│   ├── инфраструктурные объекты
│   └── локальные проблемы
├── 14 городских мер
│   ├── стоимость
│   ├── район или весь город
│   ├── направление
│   ├── лаг
│   ├── положительные и отрицательные эффекты
│   └── синергии и несовместимости
├── City Engine
│   └── официальный Score и audit trail
└── Synthetic Population
    ├── жители районов
    ├── бизнес
    ├── городской транспорт
    ├── социальные службы
    └── бюджетный аналитик
```

Основой остаётся официальный датасет. Продукт не придумывает числовые эффекты: City Engine буквально воспроизводит заданные районы, показатели, меры, ограничения и формулу.

## 3. Синтетическое население

Для MVP достаточно 30–50 виртуальных жителей, объединённых в восемь архетипов:

- родители с детьми;
- студенты и молодёжь;
- автомобилисты;
- пользователи общественного транспорта;
- жители с экологическими приоритетами;
- малый бизнес;
- пожилые жители;
- городской бюджетный аналитик.

Каждый агент получает район, социальный контекст, приоритеты, уровень доверия, влияние и начальную позицию:

```json
{
  "id": "nura_parent_01",
  "district": "nura",
  "archetype": "parent",
  "age_group": "30–45",
  "household": "семья с детьми",
  "priorities": {
    "S1": 1.0,
    "S2": 0.8,
    "T2": 0.7,
    "E1": 0.4
  },
  "trust_in_government": 0.55,
  "influence": 0.65,
  "stance": 0,
  "memory": []
}
```

Персоны являются сценарной моделью, а не репрезентативным опросом населения. Это ограничение нужно явно показывать в интерфейсе и презентации.

## 4. MiroFish-подобная симуляция

```text
Пользователь выбирает 5 мер
        ↓
City Engine рассчитывает изменения
        ↓
Создаётся reality seed по Астане
        ↓
Агенты оценивают личный и районный эффект
        ↓
Раунд 1: независимые реакции
        ↓
Раунд 2: поддержка, возражения и коалиции
        ↓
Report Agent формирует итоговый анализ
```

### Reality seed

Агентам передаётся immutable snapshot:

- выбранные меры и их стоимость;
- изменения показателей каждого района;
- общий Score и его компоненты;
- критические пороги;
- районы, получившие прямые инвестиции;
- список фактов, которые нельзя изменять.

### Раунд 1

Каждый агент независимо отвечает:

```json
{
  "agent_id": "nura_parent_01",
  "support": 0.72,
  "benefits": ["S1 в Нуре вырос с 38 до 48"],
  "concerns": ["транспортная доступность не изменилась"],
  "question": "Почему транспортный дефицит остался без решения?"
}
```

### Раунд 2

Агент видит короткие тезисы связанных стейкхолдеров и может:

- поддержать один тезис;
- оспорить один тезис со ссылкой на рассчитанный факт;
- предложить один компромисс;
- ограниченно изменить свою позицию.

### Report Agent

Формирует:

- общий уровень поддержки;
- реакцию каждого района;
- основные коалиции;
- конфликт интересов;
- недополучившие внимание группы;
- главный политический риск;
- предлагаемую замену одной меры.

Предложение AI не применяется автоматически. Пользователь подтверждает замену, после чего City Engine повторно валидирует сценарий и рассчитывает официальный Score.

## 5. Представление города в UI

Главный экран строится вокруг упрощённой SVG-карты пяти районов, а не тяжёлой GIS- или 3D-модели.

```text
┌──────────────────────────────────────────────────────────────┐
│ Астана · горизонт 8 кварталов       Бюджет 82/100 · 4/5 мер │
├────────────────┬─────────────────────────┬───────────────────┤
│ Каталог мер    │ Карта Астаны            │ Эффект сценария   │
│                │                         │                   │
│ Транспорт      │   Есиль                 │ 52.56 → 56.54    │
│ Экология       │       Нура              │                   │
│ Соц. сфера     │ Сарыарка                │ Среднее     +1.2 │
│ Безопасность   │       Алматы            │ Минимум     +3.8 │
│ Сервисы        │   Байконур              │ Критических 2→0  │
├────────────────┴─────────────────────────┴───────────────────┤
│ Временная шкала: сейчас ─ Q1 ─ Q2 ─ Q3 ─ ... ─ Q8          │
├──────────────────────────────────────────────────────────────┤
│ Совет города: 68% поддержки · 2 конфликта · 1 слепая зона   │
└──────────────────────────────────────────────────────────────┘
```

Для каждого района показываются:

- текущий и будущий районный индекс;
- два самых слабых показателя;
- объём прямых инвестиций;
- выбранные городские и локальные меры;
- поддержка сценария агентами;
- предупреждение, если район не получил прямых мер.

## 6. Паттерны CoSI

Из Hamburg CoSI следует взять четыре решения:

1. **Карта как главный рабочий объект.** Показатели и инфраструктура всегда привязаны к территории.
2. **Переключаемые тематические слои.** Школы, медицина, транспорт, экология, безопасность и обращения.
3. **Screening Tool.** Пользователь меняет параметры и сразу видит будущую конфигурацию района.
4. **Прослеживаемость решения.** Любой итоговый показатель можно раскрыть до исходных данных и применённых изменений.

Главное отличие продукта — поверх детерминированного городского расчёта запускается моделирование социальной реакции.

Источник: [официальная страница CoSI города Гамбург](https://www.hamburg.de/politik-und-verwaltung/behoerden/finanzbehoerde/informationsfilm-zu-cosi-1176176).

## 7. Ключевой пользовательский сценарий

1. Пользователь выбирает строительство школы в Нуре.
2. Нура подсвечивается на карте.
3. Интерфейс показывает затронутые показатели и снижение остатка бюджета.
4. Timeline визуализирует лаг до появления эффекта.
5. После запуска карта переходит в состояние «через 8 кварталов».
6. Score раскладывается на среднее, слабейший район и критические показатели.
7. Агенты формируют реакции и вступают во второй раунд обсуждения.
8. Районы без прямых вложений показывают возражения.
9. Report Agent предлагает более сбалансированную замену.
10. Пользователь применяет её в черновик, после чего City Engine заново рассчитывает результат.

## 8. Что собрать за 3–4 часа

### Обязательно

- SVG-карта пяти районов;
- переключение `до / после`;
- каталог 14 мер;
- бюджет и проверка конфликтов;
- Score по официальной формуле;
- шесть–восемь типов агентов;
- два коротких раунда;
- панель `консенсус / конфликт / рекомендация`;
- детерминированный fallback при недоступности LLM.

### Не делать в MVP

- настоящую 3D-Астану;
- подробную геометрию улиц и зданий;
- спутниковые и потоковые данные;
- тысячи агентов;
- прогноз реального общественного мнения;
- Neo4j, Zep и полный OASIS runtime;
- авторизацию и базу данных.

## 9. Экстренный план на троих: осталось 3 часа

Работа делится на три вертикальных продуктовых потока. Каждый разработчик отвечает за демонстрируемый результат, а не только за отдельный технический слой.

### Разработчик 1 — «Сценарий акима»

Владеет полным путём выбора и расчёта решений:

- загрузка и нормализация официального датасета;
- каталог 14 мер;
- выбор района для локальной меры;
- бюджет `0–100`;
- проверка пяти решений, конфликтов и ограничений;
- точный City Engine;
- контрольные значения `52.55768` и `56.54307`;
- контракт `Scenario → EvaluationResult`;
- endpoint `POST /evaluate` или эквивалентная чистая функция.

**Результат:** пользователь составляет валидный сценарий и получает правильный Score. Этот поток имеет абсолютный приоритет перед оптимизатором, дополнительными пресетами и сложным audit UI.

### Разработчик 2 — «Цифровая Астана»

Владеет визуальным представлением города и результата:

- SVG-карта пяти районов;
- каталог мер и состояние выбранного портфеля;
- бюджет `потрачено / доступно`;
- состояния `до / после`;
- цветовая шкала качества жизни;
- слабые и критические показатели;
- Score breakdown;
- компактный timeline появления эффектов;
- один экран без маршрутизации и второстепенных страниц.

**Результат:** жюри понимает последствия решения без чтения исходного датасета и формул.

### Разработчик 3 — «Общество города и интеграция»

Владеет MiroFish-подобной симуляцией и воспроизводимым запуском:

- 6–8 архетипов;
- synthetic population;
- первый раунд независимых реакций;
- второй раунд возражений и поддержки;
- Report Agent: consensus, conflicts, blind spots, suggested swap;
- deterministic fallback по тому же `CouncilResult`;
- соединение UI с City Engine;
- Docker Compose, `.env.example`, healthcheck и demo fixtures.

**Результат:** система показывает социальный конфликт и предлагает компромисс, но не изменяет официальный Score.

### Расписание на оставшиеся 3 часа

| Время от старта | Разработчик 1 | Разработчик 2 | Разработчик 3 | Общий gate |
|---|---|---|---|---|
| 00:00–00:15 | фиксирует `Scenario` и `EvaluationResult` | фиксирует layout и UI states | фиксирует `CouncilResult` | три контракта заморожены |
| 00:15–00:45 | два контрольных расчёта | основной экран на fixture JSON | fallback council и API stub | у каждого есть работающий артефакт |
| 00:45–01:15 | validator и все hard constraints | выбор мер, budget guard, `до / после` | соединение UI с `/evaluate` | работает `выбор → Score → карта` |
| 01:15–01:45 | audit data и критические тесты | Score breakdown и районные состояния | два agent rounds и Report Agent | полный happy path без обязательного live LLM |
| 01:45–02:15 | CLI/evaluator entrypoint | council panel и swap preview | live structured output с timeout | MiroFish-подобный сценарий работает или уходит в fallback |
| 02:15–02:30 | smoke tests | ошибки и визуальная полировка | Docker и clean run | feature freeze |
| 02:30–03:00 | только P0-блокеры | только P0-блокеры | README, два прогона демо и backup fixtures | готовая демонстрация |

### Stop rules

- Если через 45 минут нет двух точных fixtures, разработчик 1 прекращает все дополнительные функции.
- Если к `01:15` не работает `выбор → Score → карта`, разработчик 3 прекращает live AI и чинит интеграцию.
- Если live LLM не даёт schema-valid ответ за 15 минут, используется deterministic fallback.
- Если SVG-карта тормозит UI, она заменяется пятью районными блоками; расчёт и объяснимость важнее геометрии.
- В `02:30` начинается feature freeze. После него нельзя добавлять экраны, агентов или новые сценарии.
- Последние 30 минут используются только для P0-блокеров, README, резервных fixtures и двух полных прогонов демо.

### Что сознательно вырезано

- настоящая GIS-карта и 3D;
- базы данных и авторизация;
- произвольная загрузка документов;
- Neo4j, Zep и OASIS;
- больше двух агентных раундов;
- больше одного suggested swap;
- полноценный optimizer, если он не готов к 1:45;
- отдельная мобильная версия.

### Командное правило

Все трое работают через сохранённые JSON fixtures. Разработчик 2 не ждёт backend, разработчик 3 не читает сырой датасет, а разработчик 1 не зависит от UI или LLM. Изменение общего контракта после первых 15 минут требует согласия всех троих.

## Позиционирование

> **Синтетическая Астана — интерактивная модель города, в которой математический движок показывает, что изменится, а общество AI-агентов — для кого решение окажется выгодным и какие конфликты оно создаст.**

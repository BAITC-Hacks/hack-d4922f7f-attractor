# Контракт API для frontend V1

Контракт предназначен для интерфейса акима и сотрудников. Сервер остаётся источником
истины для каталога, ограничений, валидации и расчёта. Типы TypeScript без runtime-
зависимостей находятся в `packages/contracts/src/v1.ts` и экспортируются из пакета.

## Общие правила

- JSON в UTF-8. Успешный ответ возвращает HTTP 200; бизнес-ошибки выбора представлены
  `valid: false` и `issues`, а не HTTP-ошибкой.
- Клиент может передавать `X-Request-Id` (UUID или другой непустой trace ID). Сервер
  возвращает фактически использованный ID в заголовке `X-Request-Id`; для ошибки он
  также дублируется в `error.request_id`. Если заголовок не передан, ID создаёт сервер.
- Для JSON POST клиент отправляет `Content-Type: application/json`. Все вызовы чтения
  и вычисления безопасно повторять; сервер не сохраняет выбор как сценарий.
- Ошибка протокола/сервера имеет форму `ApiErrorResponse`: `{ "error": { "code",
  "message", "request_id", "retryable", "details?" } }`. Стабильные коды V1:
  `INVALID_REQUEST`, `CATALOG_VERSION_NOT_FOUND`, `VALIDATION_FAILED`,
  `EVALUATION_REQUIRES_VALID_SELECTION`, `ALTERNATIVES_REQUIRES_VALID_SELECTION`,
  `RATE_LIMITED`, `INTERNAL_ERROR`. Ошибка версии каталога может содержать доступные
  версии в `details`.
- Все тела запроса кроме `GET /catalog` несут `versions` из загруженного каталога:
  `catalogVersion`, `dataSnapshotId`, `modelVersion`, `rulesVersion`. Версионное
  несовпадение возвращается как `VERSION_MISMATCH` issue, чтобы интерфейс мог предложить
  перезагрузить каталог.

## Эндпоинты

### `GET /catalog`

Загружает единственный источник для селекторов и подписей интерфейса. Необязательный
query-параметр `catalogVersion` фиксирует запрошенную версию; без него сервер возвращает
актуальный официальный снимок. Ответ `CatalogResponse` содержит версии, 5 районов с
долями населения и базовыми значениями, 10 показателей с весами/единицами, 14 мер с
направлением, областью действия, ценой, лагом и эффектами, а также правила и синергии.
Сумма долей населения равна 1; ID районов: `esil`, `almaty`, `saryarka`, `baykonur`,
`nura`. ID мер — `M1`…`M14`; показатели: `T1`, `T2`, `E1`, `E2`, `S1`, `S2`, `B1`,
`B2`, `C1`, `C2`.

### `POST /v1/validate`

Принимает `SelectionRequest` с версиями и массивом `{ measureId, districtId }`. Проверяет
ровно пять уникальных мер, допустимость района для районной/городской меры, бюджет 100,
лимит двух мер на направление и конфликты M1/M3 глобально, M4/M7 и M5/M13 в одном
районе. Ответ `ValidateResponse`: `valid`, список `{ code, message, field, selectionIndexes?,
measureIds?, districtId?, limit?, actual? }`, `cost`, `remainingBudget`. Невалидный выбор
остаётся полноценным ответом и не запускает расчёт.

### `POST /v1/evaluate`

Принимает `SelectionRequest`. Для невалидного набора возвращает полный `EvaluateResponse`
с `valid: false`, issues, стоимостью и остатком, но `score`, `average`, `minimum`,
`criticalCount` и `decomposition` равны `null`; `districtScores` и `indicators` пусты.
Для валидного набора возвращает те же issues (пустой список), цену и остаток, итоговый
Score, Score каждого района до/после, массив показателей с before/after/delta и точную
декомпозицию изменения Score на вклад среднего, минимума и штрафа за критические значения.
Критично значение строго меньше 40; эффекты сначала суммируются, затем ограничиваются
диапазоном 0–100. Округление — только на отображении.

### `POST /v1/alternatives`

Принимает `AlternativesRequest`: исходные версии и выбор плюс `constraints`. `fixedSelections`
должны входить в каждый результат; опционально можно ограничить районы, число замен
(по умолчанию 1) и число результатов. Каждый `AlternativeResult` содержит полный новый
выбор, вложенный точный `EvaluateResponse`, число замен и `searchStatus`. Пока поиск не
завершён, статус `best-found`; только завершённый полный поиск может сообщить `exhaustive`.
Ответ с проблемой исходного выбора имеет `valid: false`, issues и пустые results. Все
альтернативы оцениваются тем же evaluator и проходят пользовательские ограничения до
ранжирования. Точки равенства сортируются по цене, числу замен, затем каноническому ID.

## Golden-сценарий

Стартовое состояние из официального снимка должно дать базовый диагностический Score
`52.55768`. Контрольный допустимый набор:

```json
{
  "selections": [
    { "measureId": "M7", "districtId": "nura" },
    { "measureId": "M8", "districtId": "nura" },
    { "measureId": "M10", "districtId": "nura" },
    { "measureId": "M12", "districtId": null },
    { "measureId": "M5", "districtId": "saryarka" }
  ]
}
```

Для выбранных версий каталога `POST /v1/evaluate` возвращает `valid: true`, `issues: []`,
`cost: 95`, `remainingBudget: 5`, `score: 56.54307`, `average: 58.0776`,
`minimum: 52.9625`, `criticalCount: 0`. Районные scores: Есиль 63.4275, Алматы 57.4975,
Сарыарка 56.3, Байконур 57.0675, Нура 52.9625. Декомпозиция прироста Score: `0.85064`
за среднее + `1.13475` за минимум + `2` за снятие двух критических штрафов = `3.98539`.
Проверка golden допускает числовую погрешность не больше `1e-8`; API значения не
округляет между этапами.

## Состояния интерфейса

Минимальная машина состояний для каждого запроса: `idle` → `loading` → `success` либо
`error`; изменение выбора при активном запросе переводит результат в `stale`, пока
новый ответ не совпадёт с актуальным локальным выбором. Ответы validate/evaluate со
`valid: false` — состояние `success` с блокирующими issues, а не транспортная ошибка.
Показывайте `remainingBudget`, `valid`, issues и версии в состоянии результата; при
сетевом сбое сохраняйте локальный выбор и позволяйте повторить запрос. Отмена запроса
не означает отмену или изменение серверного состояния. Для альтернатив отдельно
различайте пустой успешный результат, `best-found` и `exhaustive`.

Каталог можно кэшировать только пока открыт экран и только по полному ключу версий;
для V1 достаточно одного активного снимка. Выбор передаётся как UI-команда и не является
серверным сохранённым сценарием.
